Section 1

Executive Summary

BankApp is a full-stack banking portal built with Next.js 16, Spring Boot 4.1, and Keycloak. It enables three distinct user roles — customers, bank managers, and administrators — each with a tailored experience. The system handles customer onboarding, account management, fund transfers, beneficiary management, idempotent payments, and manager provisioning — all secured through industry-standard OAuth2 / OIDC authentication.

🔐
Secure by Default
Every API request is protected by a Keycloak JWT. Spring Boot verifies the token signature without storing credentials.
👥
Three Roles
Admin, BankManager, and User each see a different UI and have different API permissions enforced at the backend.
🏦
Full Banking Suite
Customers, accounts, transactions, transfers, payments, beneficiaries, and manager provisioning — all managed through a versioned REST API.

Section 3

System Architecture

Five services run in Docker containers on the same internal network. The browser communicates only with nginx / OpenResty on ports 80 and 443. All other services — Next.js, Keycloak, Spring Boot, and PostgreSQL — are internal only, never exposed to the host directly. JWT validation (RS256, Keycloak public key) runs in the nginx Lua layer using lua-resty-jwt — Spring Boot trusts the X-User-Roles header injected by nginx instead of parsing JWTs itself.

Section 4

Authentication & Authorization

The system uses the OAuth2 Authorization Code flow via Keycloak. The browser redirects through nginx to the Keycloak login page at /auth/. JWT validation happens in the nginx Lua layer — Spring Boot never sees raw JWTs. Instead, nginx injects the validated roles as an X-User-Roles header that Spring Security reads via GatewayAuthenticationFilter.

Custom Keycloak Theme — Keycloak uses a custom bankapp login theme (FreeMarker templates + CSS) that matches BankApp's visual design: blue primary, dark navy text, white card on light-grey background. Mounted via Docker volume ./keycloak/themes:/opt/keycloak/themes:ro and activated via realm-export.json → "loginTheme": "bankapp". The Next.js login page shows only a "Sign In" button — Keycloak handles the actual credential form, including forced temporary password change.

Login Flow

1
User visits the app
Next.js middleware detects no session → redirects to /login page.
2
Redirect to Keycloak (via nginx)
Clicking "Sign In" sends the user to https://13.202.124.135/auth/realms/bankapp/protocol/openid-connect/auth. nginx proxies /auth/* to Keycloak internally — the browser never hits Keycloak directly.
3
User authenticates on Keycloak
Keycloak displays the login form. Credentials are validated against the Keycloak user store. Passwords never touch Next.js or Spring Boot.
4
Authorization code returned
Keycloak redirects back to https://13.202.124.135/api/auth/callback/keycloak with a one-time auth code. nginx routes /api/auth/* to Next.js (before /api/* — more specific prefix wins).
5
NextAuth exchanges code for tokens
Server-side call to the Keycloak token endpoint at https://13.202.124.135/auth/realms/bankapp/... — the same public issuer the browser uses, reached via the gateway's public IP and proxied by nginx to Keycloak. One issuer URL everywhere keeps the JWT iss claim consistent and avoids OIDC discovery mismatches. Returns access_token (JWT), id_token, and refresh_token. Roles extracted from realm_access.roles and stored in an encrypted session cookie.
6
Session established — user lands on dashboard
NextAuth stores an encrypted session cookie. Every subsequent page load reads roles from the session and renders the role-appropriate UI.

API Request Flow

1
Axios interceptor attaches token
Every API call from Next.js automatically gets Authorization: Bearer <jwt> added by a request interceptor in lib/api.ts.
2
nginx validates JWT (Lua)
jwt_verify.lua runs in nginx access_by_lua_file. It fetches Keycloak's RS256 public key from http://keycloak:8080/auth/realms/bankapp (cached 1 hour in lua_shared_dict), verifies the JWT signature, and injects X-User-Roles, X-User-Email, X-User-Sub headers.
3
GatewayAuthenticationFilter reads headers
Spring Security's GatewayAuthenticationFilter reads X-User-Roles and builds a UsernamePasswordAuthenticationToken with ROLE_USER / ROLE_BANKMANAGER / ROLE_ADMIN authorities. Spring Boot never parses JWTs itself.
4
SecurityConfig enforces access
Each route is checked against the rules in SecurityConfig.java. If the role doesn't match, Spring returns 403 Forbidden before the controller method ever runs.
5
Controller handles the request
Business logic executes, DB is queried, and a JSON response is returned.

Idempotent Fund Transfer

A fund transfer moves money between two accounts and must never double-charge if the client retries — a dropped response, a double-click, or a network timeout should not result in two debits. BankApp solves this with a client-generated idempotency key: the paymentId (a UUID) is both the primary key of the payments row and the idempotency token. The entire transfer runs inside a single Spring @Transactional method in TransferServiceImpl, so the debit, the credit, the two transaction rows, and the payment record all commit together or not at all.

1
Client generates a paymentId before sending
The frontend creates a fresh UUID (crypto.randomUUID()) and includes it in the POST /api/v2/transfer body. The same UUID is reused for every retry of that one logical transfer — a new UUID is only minted for a genuinely new transfer.
2
Server looks up the paymentId first (the idempotency guard)
Inside the @Transactional method the service calls paymentRepo.findById(paymentId). If a COMPLETED payment already exists, it returns the stored PaymentResponse immediately — no second debit, no second transaction. If one exists and is still PENDING (a request already in flight), it returns 409 Conflict "Payment is already in progress".
3
Validate and persist a PENDING payment
For a new paymentId the service verifies the sender owns fromAccount, resolves the recipient by account number, and rejects same-account transfers. It then saves the Payment row with status PENDING and initiatedAt = now.
4
Move the money atomically
Balance is checked (InsufficientBalanceException if too low), fromAccount is debited, toAccount is credited, and two Transactions rows are written — a DEBIT on the sender and a CREDIT on the recipient, each with the running balanceAfter. The payment is marked COMPLETED with completedAt.
5
On failure, roll back and record why
Any exception marks the payment FAILED with the failureReason and re-throws. Because the method is @Transactional, the re-thrown runtime exception rolls the whole transaction back — no partial debit is ever left behind. The client can safely retry with the same paymentId.
6
The paymentId PK guarantees exactly-once
Because payment_id is the primary key, two concurrent retries cannot both insert a row — the database rejects the duplicate key — so at most one transfer is ever recorded for a given idempotency key.

The idempotency guard (TransferServiceImpl)

@Transactional
public PaymentResponse transfer(String email, TransferRequest request) {
    Optional<Payment> existing = paymentRepo.findById(request.getPaymentId());
    if (existing.isPresent() && existing.get().getStatus() == COMPLETED)
        return toPaymentResponse(existing.get());          // replay — no double charge
    if (existing.isPresent() && existing.get().getStatus() == PENDING)
        throw new ResponseStatusException(CONFLICT, "Payment is already in progress");

    // ... validate sender / accounts, save Payment(PENDING) ...
    try {
        // debit from, credit to, write DEBIT + CREDIT transactions
        payment.setStatus(COMPLETED);
        payment.setCompletedAt(now);
    } catch (Exception e) {
        payment.setStatus(FAILED);
        payment.setFailureReason(e.getMessage());
        paymentRepo.save(payment);
        throw e;                                           // rolls back @Transactional
    }
    return toPaymentResponse(paymentRepo.save(payment));
}
Preview before pay — GET /api/v2/transfer/preview validates the source and recipient accounts and returns the confirmed names and balances before the user commits. It is read-only and carries no paymentId. The actual transfer is a separate POST /api/v2/transfer call carrying the paymentId, keeping the preview side-effect-free.

Registration Rollback

Customer onboarding is a three-step @Transactional saga: (1) create the Keycloak user, (2) save the Customer record, (3) create the first Account. If the DB save fails at any point, the Keycloak user is automatically deleted and the DB transaction is rolled back — leaving no orphaned records anywhere.

String keycloakUserId = keycloakAdminService.createUser(...);
try {
    Customer saved = customerRepo.save(customer);   // step 2
    accountService.createAccount(accountRequest);   // step 3
} catch (Exception dbEx) {
    keycloakAdminService.deleteUser(keycloakUserId); // rollback Keycloak
    throw dbEx;                                      // DB rolls back via @Transactional
}

Lua JWT Validation Flow

On every /api/* request nginx runs access_by_lua_file /etc/nginx/lua/jwt_verify.lua which:

  1. Extracts the Bearer token from the Authorization header.
  2. Fetches the RS256 public key from Keycloak's JWKS endpoint (/auth/realms/bankapp/protocol/openid-connect/certs) — result cached in nginx shared dict to avoid a Keycloak round-trip on every request.
  3. Validates the JWT signature, exp (expiry), and iss (issuer) fields.
  4. Extracts realm_access.roles and injects them as the X-User-Roles header (e.g. ROLE_ADMIN,ROLE_USER).
  5. On any failure: returns 401 Unauthorized with a JSON body before the request reaches Spring Boot.

Every communication path in the system — from browser to database — annotated with protocol, direction, and whether it passes through nginx or bypasses it internally.

Token exchange goes through nginx — When Next.js (server side) exchanges the auth code for tokens (Flow ③) or refreshes a token, it calls the same public issuer the browser uses — https://13.202.124.135/auth/realms/bankapp. In production this backchannel call reaches the gateway's public IP and is proxied through nginx on :443 to Keycloak, exactly like a browser request. Using one issuer/hostname everywhere keeps the JWT iss claim matching and avoids OIDC discovery mismatches. The browser never sees Keycloak's internal address.

Load Balancing — nginx Upstream (Round-Robin)

Spring Boot runs as two containers from the same image on Instance 1: bankapp-api-1 (host port 8080) and bankapp-api-2 (host port 8081). The nginx gateway on Instance 2 defines an upstream block listing both, and load-balances /api/* traffic across them using nginx's default round-robin algorithm — request 1 → :8080, request 2 → :8081, request 3 → :8080, and so on. keepalive 32 keeps idle connections open so each request does not pay a fresh TCP handshake.

# api-gateway/conf.d/upstreams.conf (rendered from template at container start)
upstream spring_backend {
    server 172.31.18.69:8080;   # bankapp-api-1
    server 172.31.18.69:8081;   # bankapp-api-2
    keepalive 32;
}
Security group must allow BOTH ports. Because the gateway round-robins to :8080 and :8081 on Instance 1's private IP, Instance 1's security group inbound rule must allow TCP 8080–8081 from Instance 2's security group. If only 8080 is open, nginx cannot reach api-2: every other request stalls for the proxy_connect_timeout (10 s) before nginx marks that replica down and falls back to api-1 — so the second replica serves no traffic and users see intermittent ~10 s delays. Opening 8081 is what makes the load balancing real.

CORS Handling (TLS Termination & Allowed Origins)

Because TLS terminates at the gateway and the gateway → Spring Boot hop is plain HTTP, Spring sees its own scheme as http while the browser's Origin header is https://13.202.124.135. The scheme mismatch makes Spring treat even same-host calls as cross-origin, so Spring Security validates the Origin against an allow-list. State-changing verbs (POST / PUT / DELETE) carry an Origin header, so they are checked; same-origin GETs do not carry one and pass untouched — which is why page loads worked but "create manager" returned 403 Invalid CORS request until the production origin was allow-listed.

The allowed origins are injected via an environment variable rather than hardcoded, so the same image works in dev and prod:

# application.properties — env-driven, with a dev-safe default
app.cors.allowed-origins=${CORS_ALLOWED_ORIGINS:https://localhost,http://localhost:3000}

# .env.instance1 (Instance 1) — the public origin the browser uses
CORS_ALLOWED_ORIGINS=https://13.202.124.135
The allowed origin is the public https URL, not the internal http address. CORS is a string match against the browser's Origin header (always https://13.202.124.135) — the plain-HTTP internal hop is irrelevant to that match. An alternative enterprise approach is server.forward-headers-strategy=framework, which makes Spring honour nginx's X-Forwarded-Proto, reconstruct the request as https, and recognise it as same-origin so CORS never triggers.

Concurrency — Workers, Threads & Connection Pools

Each layer funnels concurrency down to protect the one below it. nginx is event-driven — a few worker processes handle thousands of connections without a thread each. Spring Boot (Tomcat) is thread-per-request — one thread per active request, capped by the pool. HikariCP keeps a small pool of reusable DB connections so PostgreSQL is never overwhelmed.

LayerResourceLimit (per instance)
nginx gatewayworker processesauto = CPU cores (2)

Why the DB pool is small. Throughput is bounded by the database's CPU cores, not by connection count — past (cores × 2) + 1, extra connections only add context-switching and lock contention. A small pool with fast (millisecond) turnover keeps every query fast; surplus request threads queue briefly rather than overwhelming PostgreSQL.

ARM64 / Graviton Compatibility

Alpine-based JRE images have no ARM64 variant. The original Dockerfile used eclipse-temurin:17-jre-alpine which fails on Graviton with "no match for platform in manifest". Fixed by switching to maven:3.9-eclipse-temurin-17 (Debian) for build and eclipse-temurin:17-jre-jammy (Ubuntu 22.04) for runtime. Node 20 Alpine does include an ARM64 build so Next.js is unaffected.

zram swap trick for first build — On a 2 GB instance, creating a swapfile consumed all free disk space and the Docker layer cache hit "no space left on device". zram creates a compressed RAM-backed swap device with zero disk usage: 
sudo modprobe zram
echo 536870912 | sudo tee /sys/block/zram0/disksize   # 512 MB
sudo mkswap /dev/zram0 && sudo swapon /dev/zram0 -p 100
# build runs here — 512 MB of compressed virtual swap, no disk consumed
sudo swapoff /dev/zram0  # release after build

Self-signed TLS Certificate (IP SAN)

Without a domain name the cert must include a Subject Alternative Name of type IP (not DNS). Browsers reject certs that only have the IP in the CN field. The generate-certs.sh script detects whether the argument looks like an IPv4 address and sets the SAN accordingly:

cd api-gateway/certs && bash generate-certs.sh 13.202.124.135
# Generates 13.202.124.135.crt / .key with subjectAltName=IP:13.202.124.135
# DOMAIN=13.202.124.135 → nginx loads /etc/nginx/certs/13.202.124.135.{crt,key}
